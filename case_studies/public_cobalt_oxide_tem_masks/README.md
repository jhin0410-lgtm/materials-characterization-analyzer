# Public Cobalt Oxide TEM Source-Mask Diagnostic Case

This case imports **real experimental-derived public data**, not a synthetic scientific example.

The selected file contains segmentation masks produced by the source authors from HRTEM images of cobalt oxide nanoparticles. The masks are source-produced derived data. They are not raw TEM intensity images, independent ground truth, or predictions generated by this repository.

## Source

- Dataset: *Transmission electron microscopy images and deep Learning-predicted segmentation for statistical analysis of cobalt oxide nanoparticles*
- Repository: Zenodo
- DOI: `10.5281/zenodo.14927582`
- Record version: `v1`
- License: `CC BY 4.0`
- Selected archive: `Segmented_images.zip`
- Published MD5: `63edc9b44264f8a1397bff806d58eade`
- Tracked SHA-256: `bd7816f3cf2869e4a349fc04d3e0d0464b3e14e9c8c8655f51e6e487fb59824b`

The external data retain their own license and citation requirements. The raw archive is downloaded at runtime and is not committed to this repository.

## Audited source contract

The pinned archive contains:

- 10 valid HDF5 files;
- 5 masks per HDF5 file;
- 50 source-predicted masks total;
- one `/labels` dataset per file;
- shape `5 x 4096 x 4096` per file;
- `float64` storage;
- exact binary values `0.0` and `1.0`;
- no embedded HDF5 pixel-size, synthesis-condition, or validation-label attributes.

The source filenames are retained as opaque identifiers. This workflow does not infer physical meaning from prefixes such as `Co` or `DW`.

## Processing contract

For every source mask, the workflow:

1. verifies the exact archive identity and safe ZIP structure;
2. extracts one HDF5 member at a time;
3. checks the exact dataset name, shape, dtype, and absence of unexpected attributes;
4. validates every pixel as finite and exactly binary;
5. computes 8-connected components without filtering;
6. records pixel-domain foreground and component descriptors;
7. records source-file SHA-256 and preprocessing identity for every feature;
8. deletes the temporary extracted HDF5 file before continuing.

It does **not** threshold, smooth, relabel, merge, split, remove, or otherwise re-segment the supplied masks.

## Validated real-data result

The dedicated GitHub Actions workflow processed all 50 masks and reproduced:

- 10 explicit source-file identities;
- 50 measurement identities;
- 41,040 unfiltered 8-connected components;
- 3,480 border-touching components;
- 335,566,001 foreground pixels;
- 400 long-format feature records;
- complete source SHA-256 and preprocessing-ID coverage.

These are descriptors of the supplied source-predicted binary masks. `41,040` must not be reported as a validated nanoparticle count.

## Software validation

Synthetic HDF5 archives are used only in automated tests to verify binary-value rejection, archive-path safety, connected-component calculations, deterministic output, provenance coverage, and overwrite refusal. Synthetic fixtures are not included in the case result and are not scientific evidence.

## Scientific closeout

**Evidence level: Diagnostic**

### Supported

- exact public archive acquisition and checksum verification;
- HDF5 schema and full binary-value validation;
- source-mask integrity review;
- transparent pixel-only connected-component diagnostics;
- provenance-preserving feature export.

### Not supported

- raw TEM image interpretation;
- independent segmentation accuracy or model-performance validation;
- nanometre-scale particle dimensions;
- treating each connected component as a confirmed particle;
- phase, defect, morphology-mechanism, or chemical-state claims;
- synthesis-condition comparisons;
- causal inference, prediction, optimization, or engineering release.

The main blocking issue is not software capability. The selected archive does not embed a verified raw-image-to-mask mapping, pixel calibration, independent labels, or source-backed synthesis-condition mapping. Those missing evidence contracts must be resolved before physical-size or model-validity claims are considered.
